
# Functional Requirements Document

## 1. Purpose

This document defines the functional requirements for the Delivery Standardization & Cost Optimization Platform.

The solution will ingest synthetic operational data, transform it through Bronze, Silver, and Gold layers, create a star-schema analytical model, and support Power BI reporting for delivery performance, cost optimization, productivity, missed-delivery analysis, frequency recommendations, and sustainability.

---

## 2. Functional Scope

The platform shall support the following functional areas:

1. Source-data ingestion
2. Data-quality validation
3. Data cleaning and standardization
4. Delivery-performance calculation
5. Driver-productivity analysis
6. Cost-to-serve analysis
7. Missed-delivery root-cause analysis
8. Delivery-frequency recommendations
9. Fuel and CO₂ analysis
10. Semantic-model creation
11. Power BI reporting
12. Road-level data enrichment through Python
---

## 3. Source Data Requirements

The system shall ingest the following operational datasets:

| Source Dataset | Purpose |
|---------------|---------|
| Deliveries | Delivery transactions |
| Customers | Customer master information |
| Routes | Planned route information |
| Drivers | Driver master information |
| Driver Hours | Driver productivity and overtime |
| Delivery Costs | Labor, fuel and transportation costs |
| Fuel Consumption | Fuel usage and CO₂ emissions |
| Missed Deliveries | Missed delivery reasons |
| Delivery Frequency | Current and recommended delivery frequencies |
| Date | Calendar dimension |
| Road Events | Structured road-level events generated by Python |

The system shall validate all source datasets before processing.

- Duplicate records shall be identified.
- Mandatory fields shall be validated.
- Invalid keys shall be rejected.
- Date formats shall be standardized.
- Numeric values shall be validated.
---

## 4. Bronze Layer Requirements

The Bronze layer shall store raw operational data without applying business transformations.

### Functional Requirements

- Load source CSV files into Bronze tables.
- Preserve all source records.
- Add load timestamp.
- Add source file name.
- Preserve original data types where possible.
- Log ingestion errors.
- Prevent duplicate file loads.

### Bronze Tables

- bronze_deliveries
- bronze_customers
- bronze_drivers
- bronze_routes
- bronze_driver_hours
- bronze_delivery_costs
- bronze_fuel_consumption
- bronze_missed_deliveries
- bronze_delivery_frequency
- bronze_road_events
---

## 5. Silver Layer Requirements

The Silver layer shall clean, validate, standardize, and integrate data from the Bronze layer.

### Functional Requirements

The system shall:

- Remove duplicate records.
- Standardize data types.
- Handle missing values.
- Validate business keys.
- Standardize date and time formats.
- Validate delivery quantities.
- Join delivery, customer, route, driver, vehicle, fuel, and cost data.
- Classify missed-delivery reasons.
- Categorize controllable and uncontrollable exceptions.
- Prepare business-ready analytical tables.

### Silver Tables

- silver_delivery_performance
- silver_customers
- silver_routes
- silver_drivers
- silver_driver_hours
- silver_delivery_costs
- silver_fuel_consumption
- silver_road_events
---

## 7. KPI Calculation Requirements

The system shall calculate and expose the following KPIs.

| KPI | Description |
|------|-------------|
| OTIF % | Percentage of deliveries completed On Time and In Full |
| SLA % | Service level achieved |
| On-Time Delivery % | Deliveries completed within the planned delivery window |
| Cases per Hour | Delivered Cases ÷ Driver Hours |
| Cases per Stop | Delivered Cases ÷ Stops |
| Driver Overtime | Hours exceeding scheduled driver hours |
| Cost to Serve | Total labor + fuel + transportation cost |
| Delivery Profit | Delivery Revenue − Cost to Serve |
| Fuel Consumption | Total fuel used |
| CO₂ Emissions | Fuel Consumption × Emission Factor |
| Hotshots | Urgent deliveries outside normal planning |
| Off-Day Deliveries | Deliveries made outside planned service days |
| Stops Saved | Stops reduced through frequency optimization |
| Miles Saved | Estimated miles eliminated |
| Fuel Saved | Estimated fuel savings |
| Annual Cost Savings | Estimated annual financial savings |

All KPI definitions shall be maintained in a centralized KPI dictionary to ensure consistent reporting.

## 9. Non-Functional Requirements

### Performance

- The solution shall support at least 100,000 delivery records.
- Dashboard pages should load in under 5 seconds on a standard workstation.

### Scalability

- The architecture shall support additional distribution centers, customers, routes, and delivery records without requiring redesign.

### Data Quality

- Mandatory fields shall be validated.
- Duplicate records shall be identified.
- Invalid business keys shall be logged.
- Data quality checks shall be documented.

### Security

- No confidential or proprietary company data shall be stored.
- All datasets used in this repository shall be synthetic.
- Generic naming shall be used throughout the project.

### Maintainability

- SQL scripts shall be organized into Bronze, Silver, and Gold layers.
- KPI calculations shall be documented.
- Business rules shall be documented.
- Source code shall follow a consistent folder structure.

### Deliverables

The solution shall include:

- Source datasets
- SQL scripts
- Python road-data ingestion component
- Star schema
- Data dictionary
- KPI dictionary
- Architecture diagrams
- Power BI semantic model
- Power BI report
- Complete GitHub documentation
